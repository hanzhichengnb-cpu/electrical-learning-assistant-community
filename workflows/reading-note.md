# Reading Note and Reading Bundle

Use to create or refresh human-readable learning views. A single-object Reading Note and a topic-level Reading Bundle draw knowledge only from approved Canonical content; a Scan study note may present verified source pages and unapproved Staging explanation. All are presentation, never independent knowledge truth or publication approval.

## Page-by-page detailed study notes (default for new source-range notes)

Read the workspace's current page-study and Reading Library specifications for the exact model, requirement IDs, quality statuses, build gates and publication command. Resolve the registered PDF/version and visually inspect every requested physical page. Codex writes the requirement plan, page explanation and semantic review; local code validates and renders them without inventing teaching or calling OpenAI APIs.

Before writing any page prose, follow [Source-Range Note Authoring](../references/conversation-note-authoring.md) and the workspace's current authoring contract: inspect originals and save the Staging plan, follow the authorized model and authorship roles, and conduct a separate source-to-current-body review with concrete evidence. Difficulty changes the teaching plan and review attention. Local tools never select or call a model on their own.

Before writing any new or regenerated note, follow [Teaching Foundations](../references/teaching-foundations.md). When the workspace provides V1.3, read `teaching-foundations-v1.3.md` and `page-study-note-v1.3.md`, use `page-requirements-v2`, inventory learning dependencies and perform a separate source-to-current-body schema-2 coverage/teaching review pass with exact current-body evidence. Coverage passed / teaching failed is a valid diagnostic preview, never publishable current teaching. Do not infer semantic approval from the validator.

When the workspace provides `source-annotations-v1.3.md`, read it and the linked `lecture3-compact-acceptance-v1.3.md`, then use `reading.py init-pages` for a fresh Staging model. Visually inspect the verified original PDF and image, inventory words/formulas/diagram parts and prior concepts, then author normalized original regions, stable numbered knowledge points, brief guides and complete same-page block mappings. Choose safe badge edges beside each rectangle; never use a separate number rail or cover source ink. Keep source images unchanged with independent overlays. One complete original slide is one reading unit, with attached numbers and continuous full teaching beside it. Show no crop copies by default; only a reader-requested zoom opens a local preview while keeping the complete slide and explanation available. Verify it at the shortest required window too. Bind first-use English to its teaching point, not a separate oversized glossary. Summaries and bridges are optional when they add teaching value. Use `reading.py render-model` with the default paired template. Resolve the available Node/browser runtime first (use bundled workspace dependencies when Node is absent from PATH) and pass `--node`/`--chromium` as needed; a dependency or browser failure never counts as a completed build. Use `source-slide-flow-v1` for printing: show the complete original exactly once, then continuous numbered teaching, without per-point pages, repeated originals, crops or default enlargement appendices. Aim for one readable PDF page; when necessary allow a second teaching-only page labelled with the original page and region numbers. More than two pages requires an explicit density/necessity review and remains unpassed; never delete necessary foundations, hide math or shrink unreadably. New current publication must pass the actual PDF/print evidence gate as well as this layout and the separate exact-body v2 review. Old sequential pages retain their compatibility route; do not bulk regenerate them.

Before drafting, classify every slide from its source image as cover, agenda, divider, technical, repeat or blank. Nontechnical slides get one concise orientation point, no administrative item-by-item explanation, at most 300 non-whitespace Markdown characters and one PDF page. Technical continuations need exact continued-point IDs and page-specific necessity/compression evidence. For a new model carrying `layout_compactness_contract`, bind the page-by-page `layout_review` to model and PDF hashes in the Staging library spec; a missing or stale review fails preflight. Follow the linked compact acceptance contract for the complete checklist and review schema.

For the source-annotation layout, the interactive HTML is the primary reading result. Open it directly for the user and label the PDF as a static printing copy; a PDF cannot implement the right-hand scroll rail or click-to-locate. Do not treat a visually checked print PDF as evidence that the interactive reader works. Clicking either a numbered badge or the interior of its source frame must locate the matching lesson in the right rail; overlapping frames select the smallest hit region, while personal region-marking mode retains drag selection. The build and publication preflight must verify three MacBook widths, left/right geometry, exact badge- and frame-interior-to-lesson activation, independent rail scrolling when content overflows, and outer page scrolling across slide units. A failure blocks completion even when content, PDF and their hashes pass.

The same presentation boundary applies to a user-facing **preview**: before sharing its HTML link, require an official `reading.py render-model` result whose receipt shows a passed interaction build for that exact model and HTML. Inspect the rendered point boxes and right-side lessons; merely declaring `source-annotations-v1` in JSON or placing a whole slide beside one paragraph is insufficient. If the model still has unchecked source pages, empty `knowledge_points`, or unmapped teaching, finish a small official pilot first. If the browser or renderer cannot run, keep the draft internal and report the blocker. Do not create or share a custom whole-lecture HTML fallback under the source-annotation name, even with an “unverified preview” label.

The author model is independent of this layout. A `single-model-v1` label, a claimed `reading_layout` field or a self-made PDF cannot replace the official model, paired HTML/PDF and build receipt. Before a long lecture, complete a representative sparse, formula-dense and diagram-dense pilot where present; stop batch production if any source boxes, numbered links or print pages fail. After the visual review, prepare the normal Staging library spec and run the read-only `reading.py library-preflight --spec ...` before calling the note complete or linking it as a passed result; this checks the actual HTML/PDF/receipt hashes, the authoring marker, teaching/print gates and bound all-page visual review without publishing.

Keep each source page and its corresponding full explanations together before the next page. Explain the actual concepts, formulas, derivations, diagrams and examples at a depth suited to that page. Make additions and uncertainties visible, preserve important first-use bilingual terms, and use contiguous complexity-based batches when needed. Follow the workspace specification for structural coverage, same-page `covers` references, repetition checks and separate semantic, teaching and visual review. A successful render alone does not authorize publication.

Build in Staging, save and inspect every knowledge point at 1280×800, 1100×720 and 1144×654, test badge and frame-interior clicks, keyboard/trackpad, hiding/width/zoom, attached unobstructed badges and simultaneous source/teaching, and render and inspect every PDF page. Check that the complete left slide has no local overflow and that scrolling with the pointer over it advances the outer page without changing its `scrollTop`; check that the right rail still scrolls independently. Require these measured results in the official build receipt and publication preflight for new builds. Record actual PDF pages per original slide, original/crop counts, exact teaching/math preservation, the official build receipt and bound visual-review evidence. An artifact without these remains unpassed even if its prose review passes. Title, brief and first paragraph must stay together; continuations carry meaningful source/region references. Remove decorative labels that do not teach. Test at least sparse-term, dense-formula and diagram/circuit pages when maintaining this mechanism. Repair and repeat failed checks; failed samples remain Staging. Exclude generated teaching controls/crops/print clones from personal source anchors and test with isolated data. Then publish only a fully verified note to its Reading Library. If optional Course Recall exists, refresh and validate it after publication; otherwise keep the compatible Canonical-only path. Note production creates no Candidate or pending review.

Check the workspace's project context and acceptance record before asking about presentation. If this reading mode and teaching depth have already been accepted, continue ordinary notes without another confirmation. Request a sample decision only on first adoption of a new mode or a substantial change in teaching depth or presentation; present the complete rendered sample before that decision.

## Legacy sectioned study notes (compatibility)

Existing `kind: teaching` sections keep **本节课件 → 本节生词 → 正文讲解**. Existing V1.1 Bundles and section layouts remain readable through their compatibility path; they are not the new source-range default. A Scan study note remains Staging presentation, never an approved Canonical Bundle input.

## Existing Reading Bundle

When rebuilding or refreshing teaching presentation, apply the same foundations pass and evidence-backed teaching audit before delivery. The compatibility renderer preserves its Canonical inputs; it does not automatically certify the new teaching audit. Improve explanatory sequence within approved meaning and route substantive Canonical changes through normal Review.

When the workspace already has an approved Reading Bundle manifest, inspect its local Reading contract and CLI help. Validate the manifest, check artifact status, and rebuild with the workspace's deterministic Reading tool only when requested or when a required presentation is stale. A Bundle may select only approved Canonical objects and Sections; never compose knowledge from Staging, a prior PDF, or a legacy Reading Note. Verify the built HTML/PDF and receipt, render and visually inspect every PDF page, and deliver the typeset PDF under [User-Facing Delivery](../references/user-delivery.md). Keep the Course Manifest, Bundle identity, lecture/knowledge scope, source-page provenance, sequence, and content/presentation stale reasons consistent with the workspace's approved contract. A failed build must preserve the prior complete artifact.

Do not create additional Bundles, migrate legacy notes, or generalize a single tested course/example without the user's scope and evidence. Bundle manifests, exports, and receipts stay outside Knowledge Search and Relations. Building a PDF never approves or changes Canonical knowledge.

## Single-object Reading Note

Apply the same foundations authoring/review pass, including local recaps and explanation of newly introduced supplements; keep the audit in Staging when the legacy renderer has no schema-2 review support.

1. Read the exact Canonical object and its revision. Resolve only explicitly related titles and required Source Images.
2. Reorganize approved content for learning: one-sentence understanding, recall questions, grouped formulas, intuition, problem cues, prerequisites, engineering reminder, contextual images, confusions, related titles, concise source, and a stable professional-English learning section under [Integrated Professional English](../references/professional-english.md).
3. Hide mechanical IDs/hashes in visible prose. Keep `source_object_id` and `source_revision` in hidden Reading Note metadata.
4. Reuse Source Images by relative link and never copy them into the Reading directory.
5. Preserve exactly the content between `USER-NOTES-START` and `USER-NOTES-END`, including vocabulary familiarity, memory cues and personal notes. Abort regeneration if markers are missing, duplicated or reversed.
6. Keep `10_Reading/` outside Knowledge Search and Relations. A Reading Note never becomes a second object.
7. Compare source revisions before presenting a note. Mark stale and regenerate only when the user requests or the active workflow needs the reading view.
8. Include source-grounded core terms, collocations, English problem triggers, useful distinctions, and bidirectional recall questions. Keep this material in the Reading Layer and outside Search/Relations unless an alias or Trigger was separately reviewed and approved.
9. Deliver the note under [User-Facing Delivery](../references/user-delivery.md): short notes may appear directly in the rendered conversation; long or durable notes require a typeset PDF, with optional readable HTML. The internal Reading Markdown is never the user-facing file.

Use the workspace’s approved Reading Layer/template when present. Do not treat layout rewriting as authority to change Canonical meaning or as approval of any knowledge change.
